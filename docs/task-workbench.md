# 个人任务工作台

AgentKanbanBoard 在现有 To Do 任务树上增加了持久任务调度、Codex app-server 会话和人工处理入口。使用者负责给出目标、边界和验收要求，系统负责在条件满足时启动执行、保存过程、收集交付，并在需要人决定时展示对应请求。

第一期面向个人和人工创建的任务。执行入口是本产品与本机 Codex app-server；保留的 Desktop thread 看板用于只读导入和历史管理。任务工作台没有团队权限系统、外部工单回调平台、自由拖拽工作流编辑器或后台常驻服务。

## 快速上手

### 1. 准备运行环境

安装 [Codex CLI](https://github.com/openai/codex#installing-and-running-codex-cli)。例如使用官方支持的 npm 安装方式：

```bash
npm install -g @openai/codex
codex --version
codex app-server --help
```

工作台需要所安装的 app-server 支持实验性动态工具、线程和 Turn 接口。仅能运行 `codex` 命令不足以证明所有协议兼容；连接、创建任务和任务工具调用都需要在目标版本上验证。协议不支持或连接失败时，界面会显示具体错误，不会改为调用 Desktop 来执行。

从仓库启动完整桌面应用：

```bash
npm --prefix src-ui ci
cd src-ui
npm exec tauri dev
```

开发需要 Node.js、npm、Rust stable 与平台的 Tauri 构建依赖；测试假 app-server 子进程还需要 Python 3。`npm --prefix src-ui run dev` 只启动界面预览，不能连接本地运行时或执行任务。macOS 安装包构建方法见 [README](../README_zh.md#本地构建)。

### 2. 连接账户

进入 **To Do List**，展开 **Codex 连接与账户**。可执行文件留空时，使用已保存的路径或 PATH 中的 `codex`；也可以填写绝对路径，只填写程序路径，不带 `app-server` 等参数。首次未配置路径时，也可用 `CODEX_APP_SERVER_PATH` 环境变量提供默认值。

点击 **连接** 后查看账户和模型。需要登录时，点击 **登录 ChatGPT**，打开返回的登录页面，完成后点击 **刷新账户与模型**。账户认证由 Codex app-server 负责；应用保存自己的任务数据和程序路径。

从 Finder 启动的桌面程序可能没有终端里相同的 PATH。找不到 Codex 时，应填写绝对路径；启用浏览器时还需要确保桌面进程能找到 `npx`。

### 3. 委派一个小任务

先准备一个临时工作目录，例如：

```bash
mkdir -p /tmp/agentkanban-playground
```

在 To Do 中创建“创建问候文件”，点击任务行的 **交给 Agent**，填写：

| 字段 | 示例 |
| --- | --- |
| 受理 Agent | `codex` |
| 委托人 | `user` |
| 工作目录 | `/tmp/agentkanban-playground` |
| 任务上下文 | 新建 `hello.md`，写入“你好，AgentKanbanBoard。”；只修改这个文件，并读回确认内容。 |
| 验收要求 | 文件存在、内容正确，交付中说明实际执行的检查及结果。 |
| Blocked by | 留空 |
| 交付策略 | 提交结果后由我验收 |

点击 **委派并启动**。系统持久化配置，满足依赖和工作目录占用条件后启动会话。切换任务或关闭详情面板不影响已启动的执行。

任务详情提供五个入口：

- **会话**：消息、工具输出、截图、当前问题和审批、交付与验收。
- **变更**：Codex 上报的代码变更。
- **工作区**：目录、文本或图片预览，以及显式输入的终端命令。
- **记录**：各次执行、问题、提交、消息和返工的持久记录。
- **委派设置**：角色、上下文、验收、依赖、模型、权限和浏览器配置。

Agent 提交后先进入 **待验收**。当前执行尚未结束时不能点击验收通过，避免接受一个仍在改变的交付。执行结束后，检查结果并验收；需要调整时填写具体反馈并返工。

### 4. 验证自动串联

另建“核对问候文件”任务，使用同一目录，在 **Blocked by** 中勾选“创建问候文件”。委派后，它应保持等待；前置任务的交付验收通过后，再自动进入队列执行。

这条链路可以验证：人工任务输入、自动启动、持久执行、结果提交、人工验收、依赖解除和下一任务自动启动。无需在 Desktop 中另开会话，也无需人工反复把任务标记为“进行中”。

## 任务、执行和会话的关系

业务任务持有目标和验收规则；一次执行是完成它的一次尝试；Codex Thread 保存会话上下文，一个业务任务可以在同一 Thread 上经历多次 Turn。当前实现中，一个 WorkRun 对应一个 Turn。

| 对象 | 持有内容 | 结束代表什么 |
| --- | --- | --- |
| To Do / WorkTask | 树位置、目标、委托人、Agent、依赖、验收、结果、业务状态 | 目标已验收或明确取消 |
| WorkRun | 本次提示、generation、Thread/Turn ID、执行结果、错误与时间 | 本轮执行已停止 |
| TaskInteraction | 对应执行的审批、输入请求，或可跨 Turn 等待的业务问题 | 此次问题已处理或已过期 |
| WorkEvent | 消息、工具、变更、流转、交付和返工事件 | 可追溯记录，不直接决定业务完成 |

任务状态与执行状态分开维护。旧 Desktop 看板中的“未分类、待审核、归档”等状态仍属于导入视图，不应拿来驱动新的业务任务调度。

### 状态如何推进

| 事件或决定 | 业务状态与后续行为 |
| --- | --- |
| 人工委派，无未完成依赖 | `queued`；有执行名额且工作目录可用时启动 |
| 人工委派，依赖未完成 | `waiting / dependencies`；前置完成后重新调度 |
| 调度器领取任务、启动执行 | `running`；领取的执行 ID 用于隔离迟到事件 |
| Codex 请求审批或输入 | `waiting / approval` 或 `waiting / input`；展示绑定到本次执行的请求 |
| 人处理当前有效请求 | 恢复当前执行；若还有其他请求则继续等待 |
| Agent 提出业务问题 | `waiting / question`；可以先结束 Turn，回答后再调度 |
| Agent 报告环境阻塞 | `waiting / environment`；人解决后明确恢复 |
| Agent 显式提交交付 | `review`；检查前置和子任务完成情况，保留结果与证据 |
| Turn 正常结束且有有效交付 | Human 保持 `review`；Auto 转为 `completed` |
| Turn 正常结束，但没有有效交付或真实等待 | 最多再自动续跑两轮，仍未交接则转为 `attention` |
| 执行失败或恢复状态不确定 | 需要检查记录、工作区和错误，再明确重试；不会据此标记任务完成 |
| 人暂停、取消、验收或返工 | 执行业务状态机操作，旧执行和审批不能覆盖新的任务状态 |

普通最终回答、停止流式输出、`turn/completed`、未读消息都不是业务完成凭据。`serverRequest/resolved` 只表示该请求不再待处理，不能替代用户的允许决定。

### Human 与 Auto

**Human 是默认策略。** Agent 提交结果，且执行成功结束后，由用户检查交付并点击 **验收通过**。也可以填写反馈，启动返工。

**Auto 是明确选择的交付策略。** Agent 必须通过任务工具提交结果和非空证据，依赖须完成，直接子任务须完成或明确取消；提交后的执行还必须正常结束。提交后继续执行工具或修改文件会使该提交失效，需要重新提交。

Auto 的检查是结构、依赖和执行状态层面的检查，不会独立证明所有验收条件都真实满足。`Reviewer` 只是可选择的角色配置，同样通过 Codex 执行；它不会自动获得批准权，也不会自动代替用户审核其他任务。

## 任务树、依赖和 Agent 通信

### 任务树与依赖分别表达什么

树形关系表达工作拆解和归属，不自动规定先后顺序。`Blocked by` 表达执行需要的结果，系统拒绝自身依赖、重复依赖和循环依赖。

一个业务父任务提交交付前，直接子任务必须完成或已明确取消。**取消一个依赖任务不等于满足依赖**；依赖仍然要求前置任务完成。任务不再需要该前置时，应明确调整依赖或重新规划。

这允许以任务树组织工作，同时用少量依赖表达顺序，无需维护自由拖拽的 DAG 画布。

### 提供给 Agent 的任务工具

| 工具 | 用途 | 不会产生的隐含行为 |
| --- | --- | --- |
| `task_submit_result` | 提交结果说明和验收证据 | 不跳过当前交付策略或执行终止检查 |
| `task_wait` | 等待依赖、提出业务问题或说明真实阻塞 | 不循环调用模型询问阻塞是否已消失 |
| `task_delegate` | 创建有上下文和验收要求的业务子任务 | 不自动把父子关系当成执行依赖 |
| `task_message` | 给同一任务树内的已委派任务保存上下文消息 | 不解除对方依赖、暂停或等待，也不提供已读承诺 |
| `task_continue` | 给出具体下一步，请调度器在本轮结束后续跑 | 不绕过两轮自动续跑上限 |

新业务子任务继承父任务的工作目录、权限、交付策略和浏览器设置，Agent 不能通过创建子任务扩大自身权限。当前同一任务树内的消息是持久上下文，供接收方后续符合条件的执行读取；它不是无限制的跨 Agent 即时聊天总线。

父任务在等待同目录子任务时应使用 `task_wait` 并结束当前 Turn，释放目录占用，子任务才有机会运行。父任务收到结果后重新执行，整合交付。

Codex 自己在一个 Turn 内启动的原生 subagent 与上述业务子任务不同。它们的输出和审批归属于父业务执行，业务任务工具由主执行负责调用；原生子 Agent 的结束不会直接完成业务任务。父执行释放工作目录前，运行时会等待已知活动原生子 Agent 的停止确认。

### 只有一个自动续跑控制者

业务调度器负责决定下一轮是否可以启动。运行时会暂停所管理 Thread 中继承的或新启用的 active native Goal；如果发现 Codex 已自行启动了未获调度许可的执行，会中断并关闭不确定连接。系统不会同时启用 native Goal 自动续跑和业务任务自动续跑。

## 暂停、取消、返工和恢复

**暂停与取消作用于当前业务任务节点。** 该节点当前的 Codex Turn 及其已知原生子 Agent 会被停止；业务子任务、兄弟任务不会自动暂停或取消。需要停止整棵树时，应逐个处理有关节点。工作目录在停止得到确认前保持占用，避免取消按钮一按下就启动另一个写入者。

**返工启动新执行，保留旧证据。** 从待验收、已完成或已取消任务的详情中填写具体反馈，再执行返工。旧交付与反馈进入记录，当前交付摘要失效，新的执行沿用任务上下文和工作区。返工不会执行 Git 回滚，也不会撤销先前外部副作用。

前置任务返工后，尚在排队或等待的依赖会重新检查条件；已经在执行或已完成的下游任务不会被自动批量回滚或重开。验收时也会复核当前依赖。用户仍需决定哪些已有成果受影响，并对这些任务明确返工。第一期没有全量返工影响分析。

**异常恢复优先保留不确定性。** app-server 断连、请求超时、启动失败或应用退出可能发生在操作已经执行之后。再次启动时，之前未确认的执行会进入需要处理；先检查变更和记录，再重试。恢复不会把旧审批重放到新执行，也不会把“进程已退出”解释成成功。

正常停止会先使用 Codex 的中断或终端停止接口。硬停止只能保证回收本应用启动的 app-server 本身；长命令或 MCP 后代进程是否已全部退出，还需要在目标桌面环境核验。遇到这类异常时，应确认工作区和有关进程，再恢复任务。

## 工作目录与终端

调度器最多同时持有两个 Agent 执行。工作目录经过规范化，相同目录、父子目录以及指向同一路径的别名会互斥；不同目录可以并行。没有自动创建 Git worktree 的行为，需要并行修改同一仓库时，由用户先准备独立工作目录。

**工作区** 中的手动终端也由 app-server 执行，并占用相同的目录锁。已有 Agent 或终端占用目录时，手动命令会被拒绝；先暂停并等待执行结束后再运行。终端运行期间，调度器不会在重叠目录启动 Agent。文件读取和目录浏览不需要另起 Agent Turn。

手动终端默认使用任务沙箱，界面命令超时为两分钟；终端输出与停止按钮通过进程 ID 对应。终端执行成功只表示该命令成功，不会自行提交或完成业务任务。文件预览限制在任务工作目录内，路径规范化后越界也会被拒绝。

## 可选的浏览器操作

在任务首次创建会话前，勾选 **启用浏览器操作**。工作台为该 Thread 注入：

```text
npx -y @playwright/mcp@0.0.83 --isolated --browser chrome
```

这是固定版本的 [Microsoft Playwright MCP](https://github.com/microsoft/playwright-mcp/tree/v0.0.83)，通过独立的、默认可见的 Chrome 窗口执行浏览器工具。需要本机 Node.js 18+、`npx` 与 Chrome。首次运行可能下载 npm 包；MCP 启动超时为 60 秒，带浏览器配置的 Thread 启动或恢复 RPC 超时为 90 秒。

浏览器采用 `--isolated` 内存会话，不复用用户当前 Chrome 标签页或登录资料，也不承诺退出后保留登录状态。需要登录的网站应在这个独立窗口中完成登录。工具输出与支持的图片内容显示在任务会话中；工作台没有内嵌的浏览器标签页编辑器。

MCP 被配置为 required，启动失败会明确失败；MCP 启动成功仍不代表 Chrome 已实际打开，第一次浏览器工具调用还可能暴露 Chrome 路径或运行环境问题。已有 Thread 的工作目录、角色指令、Agent 和浏览器配置已固定；因为 app-server 对已加载 Thread 的恢复不会重新应用这些启动配置，需要不同配置时请创建新任务。

## 持久化与旧看板边界

应用的 SQLite 默认位于 `~/.codex-kanban/app.db`。任务配置、依赖、执行记录、待处理交互、提交结果和消息都写入应用自己的数据表。现有 To Do 编辑使用差异合并与版本校验，避免前台旧快照覆盖后台新创建的子任务或状态。

旧同步入口仍只读 Codex Desktop 的状态 SQLite 和名称索引；标注、归档和 Thread / Task 链接只改变应用本地视图。链接现有 Desktop thread 不会让工作台接管它的执行，也不会给它发送审批或续跑请求。

没有后台 daemon。关掉详情面板、切换任务或切换旧看板时，应用进程中的调度器继续工作；**退出桌面应用会停止它拥有的 app-server**。未启动的持久排队任务可在下次打开应用后重新参与调度；上次结果不确定的活动执行需要先处理恢复状态。

## 真实桌面验收边界

自动化测试分别验证 SQLite 状态机、前端交互、审批归属、文件边界和假 app-server 子进程协议。假服务测试可以复现乱序、断连、超时、子 Agent 停止确认、Goal 与任务调度竞争等边界，但不会登录真实账户、调用模型或打开 Chrome。

发布或升级 Codex 兼容版本前，应在目标桌面环境用临时项目完成一轮实际验收：

1. 连接真实 Codex、完成账户登录和模型读取，运行一个小任务，看到消息、工具输出和文件变更。
2. 触发实际审批或问题，确认只有对应的当前请求能恢复执行；暂停后旧请求失效。
3. 分别验证 Human 交付等待验收、Auto 有证据且正常结束后完成、没有提交结果的结束不会直接完成任务。
4. 验证依赖解除后自动启动、父任务等待同目录子任务、当前节点暂停取消、同目录 Agent 与手动终端互斥。
5. 验证返工保留旧交付，断连和退出后需要核对恢复，不能重复消费旧审批。
6. 开启浏览器任务，在实际 Chrome 中访问测试页面，看到工具结果和截图；验证缺少 Chrome 或 MCP 启动失败时能理解错误。

普通浏览器预览、前端 build、假协议测试或构建出安装包，均不能替代以上真实账户与浏览器验收。当前产品也不宣称完整 Codex Desktop 功能对等、自动验证所有业务验收或自动分析所有返工影响。
