# To Do List 窄屏完整隐藏尾部列设计

## 背景与根因

上一版窄屏设计把两个日期列和操作列分别压缩到 `64px`、`64px`、`44px`，并在视口不超过 `520px` 时继续保留这三列。实际结果是尾部列仍占据 `172px`，任务和关联 Thread 被压到剩余空间，日期标题、日期值和操作文字形成竖排残片。

根因是需求理解错误：窄屏时尾部三列应完整隐藏，而不是保留紧凑宽度。上一版 CSS 文本测试还把错误的五列极窄规则写成了预期，无法发现真实界面问题。

本文档取代 `2026-07-22-todo-list-column-shrink-priority-design.md` 中关于极窄列宽的设计。

## 目标

- 宽度充足时继续显示任务、关联 Thread、预期结束日期、实际结束日期和操作五列。
- 列表容器宽度不超过 `520px` 时，从表头和每个任务行完整隐藏两个日期列和操作列，只保留任务与关联 Thread。
- 隐藏尾部列后，任务与关联 Thread 在空间允许时都至少保留 `140px`。
- 列表容器进一步窄到无法容纳两个 `140px` 和现有水平内边距时，任务与关联 Thread 才等权继续收缩。
- 页面不产生横向滚动，表头和任务行始终对齐。

## 方案

### 以列表容器宽度为准

给 To Do List 的列表卡片增加独立容器类并设置 `container-type: inline-size`。响应式规则使用 `@container`，不再依赖整个窗口宽度，因此导航栏展开、图标化、隐藏和禅模式都不会导致断点判断偏离实际可用空间。

### 两阶段列布局

1. 容器宽度大于 `520px`：沿用五列布局，任务与关联 Thread 最小宽度均为 `140px`。
2. 容器宽度不超过 `520px`：网格改成两列 `minmax(140px, 1fr) minmax(140px, 1fr)`；所有 `.todo-grid` 的第 3、4、5 个直接子元素设置为 `display: none`。
3. 容器宽度不超过 `320px`：网格改成两列 `minmax(0, 1fr) minmax(0, 1fr)`，两列等权继续收缩。

`320px` 包含两列 `140px`、任务行 `24px` 水平内边距及边框余量。第三至第五列在两个窄屏阶段都保持完全隐藏，不参与网格宽度计算。

## 组件边界

- React 仅给现有列表卡片增加容器类，不新增宽度状态、监听器或条件渲染。
- 表头与任务行继续共用 `.todo-grid`，通过一致的直接子元素序号同步隐藏列。
- 展开详情和关联面板本身不受影响；隐藏仅作用于折叠列表的五列网格。
- 任务数据、排序、分页、日期值、持久化和 Thread 关联逻辑均不改变。

## 测试与验收

- 自动化测试验证列表卡片具有容器类，并验证 CSS 包含 `container-type: inline-size`。
- 自动化测试验证 `≤520px` 时网格只有两列，且第 3～5 个直接子元素为 `display: none`。
- 自动化测试验证 `≤320px` 时前两列才改为等权可收缩布局。
- 真实浏览器在容器宽度约 `350px` 时检查：第 3～5 列表头和行单元格计算样式均为 `display: none`，任务与 Thread 可见，页面无横向滚动。
- 真实浏览器在容器宽度低于 `320px` 时检查：前两列宽度相等并继续收缩，第 3～5 列仍为 `display: none`，页面无横向滚动。
- 运行完整前端测试、生产构建和 `git diff --check`。

## 风险与约束

- 窄屏隐藏日期和操作列后，对应日期编辑、添加子任务和设置按钮暂不可见；扩大列表宽度后恢复。此次按用户要求完整隐藏，不新增替代入口。
- CSS 容器查询依赖当前 Tauri WKWebView 的现代 CSS 支持；普通 Vite 浏览器验收会直接验证运行时计算样式，避免只验证源码文本。
