# To Do List 窄屏列宽优先级设计

## 背景

To Do List 当前使用五列 CSS Grid：任务、关联 Thread、预期结束日期、实际结束日期和操作。任务列配置为 `minmax(0, 1fr)`，其余列大多使用固定宽度，因此窗口变窄时任务列会最先被压缩，任务标题过早丢失可读空间。

## 目标

- 任务列和关联 Thread 列在可用空间允许时都至少保留 `140px`。
- 窄屏时优先压缩两个日期列和操作列。
- 只有其他列达到紧凑宽度后，才继续压缩任务列和关联 Thread 列。
- 保持完整日期值、日期编辑、Thread 标签换行和行操作可用。
- 页面不因列宽策略产生横向滚动。

## 非目标

- 不改变任务数据、排序、分页和持久化逻辑。
- 不隐藏日期列或行操作。
- 不改变关联 Thread 的加载和打开行为。
- 不引入 JavaScript 宽度监听或运行时列宽计算。

## 方案

采用分阶段 CSS Grid，不改 React 组件的数据流：

1. 默认和一般窄屏阶段，任务列使用 `minmax(140px, 1fr)`，关联 Thread 列使用 `minmax(140px, 180px)`；日期列使用 `minmax(64px, 96px)`，操作列使用 `minmax(44px, 84px)`。
2. 视口宽度不超过 `520px` 时进入极窄断点，前两列改为两个等权的 `minmax(0, 1fr)`，日期列固定为 `64px`，操作列固定为 `44px`。此时任务与关联 Thread 一起继续收缩，保证页面不横向溢出。
3. 表头与任务行继续共用 `.todo-grid`，确保所有行严格对齐。

相比 JavaScript 动态测量，该方案无额外状态和重排抖动；相比隐藏日期或操作，该方案保留现有功能和信息密度。

## 响应式行为

- 宽屏：任务列获得剩余空间；关联 Thread 最大约 `180px`；日期和操作保持现有舒适宽度。
- 一般窄屏：任务与关联 Thread 均不低于 `140px`；日期列和操作列先向各自紧凑宽度收缩。
- 极窄屏：固定功能列已达到紧凑宽度后，任务与关联 Thread 再共同让出空间；内部文本继续使用截断或换行，网格本身不产生水平溢出。

`520px` 断点由五列 `452px` 的常规最小总宽度，加上列表和行的水平内边距及边框余量得出。

## 测试与验收

- 增加可确定性检查，验证 `.todo-grid` 的常规列定义为任务和关联 Thread 设置 `140px` 下限，并让日期、操作列具有更小的收缩下限。
- 验证极窄断点允许前两列继续收缩，且没有为网格设置强制最小总宽度或水平滚动。
- 运行 To Do 相关前端测试、完整前端测试和生产构建。
- 在约 `650px` 内容宽度检查：任务和关联 Thread 均至少 `140px`，日期与操作列已优先变窄，Thread 标签可换行。
- 在低于常规最小总宽度的极窄尺寸检查：任务和关联 Thread 才开始继续收缩，页面无横向滚动。

## 风险与边界

- 日期列收窄后，表头可能换行，但日期值仍完整显示；这是为任务信息让出空间的预期行为。
- 极窄视口无法同时保证两列 `140px` 下限与无横向滚动，因此明确采用“其他列先到最小值、前两列最后收缩”的降级顺序。
