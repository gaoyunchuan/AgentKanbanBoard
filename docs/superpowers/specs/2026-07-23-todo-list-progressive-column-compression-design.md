# To Do List 动态列宽分阶段压缩设计

## 状态

本设计取代以下旧设计中的固定容器断点和前两列等权压缩规则：

- `2026-07-22-todo-list-column-shrink-priority-design.md`
- `2026-07-22-todo-list-hide-trailing-columns-design.md`

保留旧设计中“尾列必须完整隐藏、不能残留窄轨道”和“页面不得产生横向滚动”的约束。

## 目标

To Do List 宽度变小时，不给“任务”和“关联 Thread”设置固定初始宽度，而是保留开始压缩前两列的实际计算宽度。空间不足时按明确阶段处理：

1. 操作列先压缩，到达安全下限后完整隐藏。
2. 实际结束日期列再压缩，到达安全下限后完整隐藏。
3. 预期结束日期列最后压缩，到达安全下限后完整隐藏。
4. 三个尾列全部隐藏后，关联 Thread 单独压缩至 `180px`。
5. 然后任务单独压缩至 `240px`。
6. 仍需继续变窄时，任务与关联 Thread 按 `240:180`，即 `4:3` 的比例一起缩小。

如果开始压缩时某个前置列已经小于对应阈值，不反向放大该列，直接跳过它的单列压缩阶段。

## 为什么需要运行时测量

CSS 容器查询只能根据当前容器宽度选择静态规则，无法记住“开始变窄前这两列实际是多少像素”。继续使用固定断点会出现两类偏差：

- `minmax(..., 1fr)` 会让任务列先吸收容器宽度变化。
- 固定 `240px`、`180px` 会改变宽屏下现有的自然布局，不符合“现在多宽就保持多宽”。

因此使用 `ResizeObserver` 保存上一次未压缩布局的实际列宽，再把分阶段计算结果通过 CSS 自定义属性应用到所有 `.todo-grid`。初始宽度来自浏览器计算结果，不在代码中硬编码；`240px` 和 `180px` 只作为尾列全部消失后的压缩阶段阈值。

## 布局基线

列表容器内部的表头仍是测量基准，表头和每个任务行仍保持五个顺序一致的直接子元素：

1. 任务
2. 关联 Thread
3. 预期结束日期
4. 实际结束日期
5. 操作

在未进入压缩状态时，继续使用现有自然网格：

```css
grid-template-columns:
  minmax(140px, 1fr)
  minmax(140px, 180px)
  minmax(64px, 96px)
  minmax(64px, 96px)
  minmax(44px, 84px);
```

每次容器处于自然布局且宽度稳定时，记录：

- 网格内容区宽度。
- 五个列轨道的实际计算宽度。

第一次检测到容器变窄时，使用上一次记录作为本轮压缩基线。这样任务和关联 Thread 会从真实宽度开始冻结，而不是被替换为预设宽度。

## 压缩计算

计算逻辑抽成不访问 DOM 的纯函数。输入为基线五列宽度和当前网格内容区宽度，输出为五列目标宽度与三个尾列的可见状态。

设基线总宽度与当前内容区宽度之差为 `deficit`。压缩顺序如下：

| 阶段 | 变化列 | 结束条件 |
| --- | --- | --- |
| 1 | 操作 | 从实际基线宽度缩到 `44px` |
| 2 | 操作 | 仍不够时整列变为 `0px` 且 `display: none` |
| 3 | 实际结束日期 | 从实际基线宽度缩到 `64px` |
| 4 | 实际结束日期 | 仍不够时整列变为 `0px` 且 `display: none` |
| 5 | 预期结束日期 | 从实际基线宽度缩到 `64px` |
| 6 | 预期结束日期 | 仍不够时整列变为 `0px` 且 `display: none` |
| 7 | 关联 Thread | 单独缩到 `min(基线宽度, 180px)` |
| 8 | 任务 | 单独缩到 `min(基线宽度, 240px)` |
| 9 | 前两列 | 按阶段 7、8 的结果宽度比例同步缩小 |

尾列从安全下限切换到隐藏时允许出现空白缓冲区，空白由后续容器收窄逐步消耗。不能让刚隐藏尾列释放出的空间反向扩大任务或关联 Thread，否则会违反前两列冻结规则。

最终比例阶段通常为 `240:180`。如果基线宽度已经低于某个阈值，则使用 `min(基线宽度, 阈值)` 得到的实际阶段终点比例，禁止先放大再压缩。

所有宽度结果必须钳制到非负值。当前内容区小于前两列总宽度时，前两列仍必须收缩到可用宽度内，不能制造横向滚动。

## DOM 与 CSS 接口

新增一个专用布局 hook，职责只有：

- 观察 `.todo-list-container` 的 inline size。
- 从表头五个直接子元素读取实际宽度。
- 管理当前压缩基线。
- 调用纯函数计算布局结果。
- 在列表容器上写入五个 CSS 自定义属性和尾列隐藏状态。

容器通过以下 CSS 自定义属性统一驱动表头与所有任务行：

```text
--todo-task-column-width
--todo-thread-column-width
--todo-expected-column-width
--todo-actual-column-width
--todo-actions-column-width
```

尾列隐藏使用容器 `data-*` 状态选择器控制对应直接子元素 `display: none`。隐藏列同时设置为 `0px` 网格轨道，保证表头和任务行都没有残留空间。

组件卸载时必须断开 `ResizeObserver`。布局 hook 不修改任务数据，不参与任务状态、排序、分页、日期编辑或 Thread 关联逻辑。

## 初始窄窗口

如果页面首次打开时已经很窄，没有可供回溯的宽屏基线：

1. 在布局阶段读取自然五列网格的计算宽度。
2. 以五列轨道总宽度作为所需基线宽度。
3. 以容器当前内容区宽度计算已有缺口。
4. 立即执行相同的尾列和前两列压缩算法。

这保证首次打开窄窗口不会依赖用户先放大再缩小，也不会出现一帧可交互的横向滚动布局。

## 重新变宽

同一个基线内，容器变宽时使用同一纯函数反向得到布局：

1. 前两列按原比例恢复到 `240px / 180px` 或实际阶段终点。
2. 任务恢复到基线宽度。
3. 关联 Thread 恢复到基线宽度。
4. 预期结束日期、实际结束日期、操作按压缩顺序的反方向恢复。

当内容区恢复到本轮基线宽度或更宽时，清除临时 CSS 自定义属性和隐藏状态，回到自然网格，并重新记录最新计算宽度作为下一轮基线。

## 测试与验收

### 纯函数测试

覆盖以下边界：

- 缺口为 `0` 时五列保持基线宽度。
- 操作列只缩小到 `44px`，随后完整隐藏。
- 实际结束日期只缩小到 `64px`，随后完整隐藏。
- 预期结束日期只缩小到 `64px`，随后完整隐藏。
- 任一尾列隐藏后宽度严格为 `0`。
- 三个尾列隐藏前，任务和关联 Thread 始终等于基线宽度。
- 尾列全部隐藏后，关联 Thread 先单独缩到 `180px`。
- 关联 Thread 到达阈值后，任务再单独缩到 `240px`。
- 后续保持 `4:3` 比例缩小。
- 基线前两列小于阈值时不反向放大。
- 极小宽度下结果非负且两列总宽度不超过可用宽度。

### 组件测试

覆盖：

- 列表容器安装响应式布局 hook。
- 五个 CSS 自定义属性同步应用于表头和任务行。
- 隐藏状态同时作用于表头和任务行的同一列。
- 卸载时断开 observer。

### 真实浏览器验收

从宽屏开始连续减小视口，而不是只验证两个静态断点。每个阶段读取表头和首个任务行的计算宽度、`display` 和页面溢出状态，证明：

- 前三次压缩过程中任务和关联 Thread 保持捕获宽度。
- 尾列按操作、实际结束日期、预期结束日期的顺序完整隐藏。
- 尾列全部隐藏后，Thread 单独到 `180px`，任务再单独到 `240px`。
- 继续缩小时，前两列保持 `4:3`。
- 表头与任务行始终对齐。
- `scrollWidth <= clientWidth`。
- 浏览器控制台错误为 `0`。

## 非目标

- 不改变宽屏时五列的自然宽度定义。
- 不改变尾列的内容、编辑能力或操作入口。
- 不修改任务数据、分页大小、树结构、排序或 Thread 关联。
- 不引入用户可配置列宽或拖拽调整列宽。
